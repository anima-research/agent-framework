- **The reply judge (`judge` wake rules), where it didn't do what 0.28.0's notes on it say, and still didn't in 0.34.0:**
  - 0.28.0's notes say a pending batch is judged "by the rule as it is when the judge is asked", but a batch pending when gate.json was reloaded was judged by its rule's instructions from before the edit. A batch is now judged by its rule as the rule is when the judge is asked, and a reload clears the changed rules' state and puts the new rules in force before it sends their pending batches. A batch whose rule a change removes, or makes another kind, goes as it was batched. A judge rule's batch takes the judge's path, held or delivered without the judge as any judge rule's batch is when its call is refused, and is judged by the instructions it was batched under, or by those of the call of its rule it waited behind. A debounce rule's batch is delivered without the judge.
  - 0.28.0's notes say the judge is told about "other rules' pending batches", but it wasn't told about other judge rules' batches being decided or held, or about events buffered behind a running turn. It's now told about every pending batch but the one it's asked about: besides what 0.34.0 listed, other judge rules' batches being decided or held (with what a held one waits for), as "maybe", and events buffered while a turn runs or the host is quiesced, which wake the agent once neither holds them, unless their channel is held then, or only may, as a debounced batch does, where each event delivery gives the agent has a message of its own written for it; an event whose channel is held when the judge is asked isn't counted. It lists eight, soonest first, and says how many more there are and how many of those are only "maybe". `EventGate.upcomingWakes` lists them too, leaving out a given rule's batches and buffered events. A gate made without a `judge` function delivers a judge rule's batch as it delivers a debounce's, but 0.34.0's `upcomingWakes` listed it as a batch that goes to the judge, only a maybe. It's now listed as a debounced batch, certain where a debounced batch is.
- **Corrections to 0.28.0's notes on the judge:**
  - "the request the agent would send if woken now, `previewActivation`'s dry run": the dry run leaves out what modules' `gatherContext` and MCPL servers' `beforeInference` would inject.
  - "It always uses membrane's native formatter": it asks for it, and a membrane whose own formatter is OpenAI Responses', on that adapter outside its subscription mode, keeps its formatter whatever a request asks.
  - "`maxInputTokens`: default 90,000, under the 100K line": the budget is met by an estimate, at a ratio that starts at three characters a token and follows what each response reports. A request on text denser than that ratio can carry more: code, or Chinese, Japanese or Korean text, before a response has reported on such text or after the ratio has followed sparser text. So can one whose newest message alone is over the budget, since that is always shown.
  - "`cacheTtl`: `"5m"` (the default) or `"1h"`": on Bedrock, membrane drops it and Bedrock's default applies.
  - "On wait it doesn't, and the events stay in context, as for `defer`": the events are in the agent's context when they're stored as they arrive, as MCPL's channel and push events are, apart from a coalesced push its server sends deferred, which waits outside the context until the server renders it for a turn, and as the framework's own modules store the message an event of theirs carries; a wait, like `defer`, adds nothing more. The judge's own prompt and `wake_add_rule`'s `judge` parameter, which said the events stay in context too, now say that what was stored as it arrived stays stored for when the agent is next woken.
