- An agent is now told when a rule's reply judge keeps failing. When the judge fails 3 times in a row for one wake rule, the gate writes a `[Gate]` notice. It writes it as it writes a batch's row: into the delivery agent's slot, with the audience that the batch's events name. Where they name none, it is a write that names no agent. The notice names the rule and gives the newest failure in the words that `gate_status` gives. It says what the rule's batches now do: under `onError: "wake"` they are delivered with no judgement, and under `"skip"` they don't wake the agent. The row's kind is `gate-judge-failing`, and it carries `policyName`. When the judge next gives a verdict for that rule, a second notice says that it answers again, of kind `gate-judge-answers`. Neither notice wakes anybody. Under `"wake"`, the gate writes the failing notice first, and then the batch wakes the agent.
- A failing batch can reach nobody, because each of its events is held or names no recipient. Such a batch writes no notice, and the next failure that reaches someone writes it. One such notice is open at a time, for the first rule to reach 3 failures in a row. Another rule's failures write none while it is open, and `gate_status` shows them. The notice ends without a second notice when its rule is removed or its behavior changes. A judge call that was out when its rule changed or was removed doesn't count for the rule as it is now. After a notice ends, the next failure of a rule with 3 or more failures in a row writes a new notice. A failing notice that can't be written is logged, and the rule's next failure tries again; an end that can't be written is tried again at the rule's next verdict. The notices are kept in memory, so a host that starts anew can tell them again.
- `wake_add_rule`'s description of `judge` says that the host tells the agent one time when the judge keeps failing for a rule.
