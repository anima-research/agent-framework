- Every problem a wake rule has is named, where these used to change what a rule does without a word:
  - a `behavior` that isn't `"always"`, `"defer"`, `"skip"` or an object holding one of `debounce`, `rate_limit` and `passive_sample`, which was saved as `"always"`, waking on every event the rule matches. That covered a typo such as `"deffer"`, and in membrane's XML tool mode the object form `wake_add_rule`'s description showed, since there `behavior` arrives as text;
  - a match field of the wrong type, such as `tagsAny: "chat:ambient"`, `channel: 12345`, `match: "discord"` or a `filter` whose `type` isn't `text` or `regex`, and an entry of the wrong type, or `""`, in a list, which were dropped, so the rule matched more than it named;
  - a field name that's a slip for one the gate reads at that level: the same ignoring case; one edit away, or more for a long name, a quarter of what follows the part the two names share (`pasthrough`, `keyby`, `polices`); or, at three characters or more, a part of it (`tags`, `interval` for `refillIntervalMs`). It was ignored, so the field meant was missing: `pasthrough: true` made a governor consume the events it should let fall through. Each field the name could be a slip for is named (`tags` for `tagsAny`, `tagsAll` or `tagsNone`);
  - a field the gate reads at another level of the rule, such as a match's `tagsAny` beside `name`, or a filter's `pattern` straight in `match`, which was ignored, so the rule matched more than it named. It's named with where the gate reads it: `Policy "quiet": it has "tagsAny", a field of "match", which the gate doesn't read here, so the rule matches every event.`;
  - a `rate_limit` or `passive_sample` `keyBy`, or a `resets`, of the wrong type, which was dropped;
  - a behavior object holding two kinds, of which `debounce`, then `rate_limit`, then `passive_sample` was used, whatever their order.
- `wake_add_rule` and `addGatePolicy` refuse a rule with any problem, naming every one, those of each kind a behavior object holds included, and save nothing, since their caller is there to fix it. `wake_add_rule`'s own parameters are checked the same way: a slip of one is refused, and so is a field of `match`, `rateLimit` or `passiveSample` given as a parameter of its own, such as `tagsAny`, which used to be saved without it, naming the parameter it belongs in. Any refusal of `wake_add_rule`'s also names each other parameter it doesn't take, which a saved rule's `ignoredFields` names.
- gate.json and the host's starting rules (`FrameworkConfig.gate.config`) are what a deployment already runs, so there a rule with a problem is read the way the gate read it before, and each problem is named in `gate_status`'s `errors` and a `[gate]` log line; the rest of the file loads. A rule that skips or defers is read past its problem the same way, holding back what it held back before, and its note says so: `Read so, it skips every event it now matches, as earlier releases did.` A rule is left out only where the gate refused it before: a rule that isn't an object or has no `name`; a behavior that's a list or holds none of the three kinds; a `rate_limit` or `passive_sample` that isn't an object or lacks `tokens`, `refillIntervalMs` or `every`, or has `tokens` at or under 0; a `debounce`, `tokens`, `refillIntervalMs` or `every` that isn't a finite number; an invalid regular expression in a `filter`; and a `passthrough` that isn't a boolean, or is `true` on a behavior that doesn't count. Under a default that holds events back, `"skip"` or `"defer"`, a gate.json or starting config that leaves out a rule that could wake the agent isn't used, as before, since that would hold back what the rule was written to wake on: a start runs the host's starting rules, or none, which hears every event, and a reload keeps the rules in force. A later start doesn't add starting rules that would leave gate.json unused that way, and says so. So, wherever the gate loaded the file before, no event that woke the agent before goes quiet. An empty entry in `scope`, which only narrows a rule, since no event's type is `""`, is read as written whatever the rule does.
- A number outside the gate's range is read the way the starting rules ran it, in gate.json too, which the gate refused whole for one before: a `debounce` outside 100 to 300000 ms at its nearest bound; a `passive_sample` `every` at or under 0 as 1, and a fractional one as its next whole number; and a `rate_limit` `refillIntervalMs` at or under 0 as a bucket that never refills, so the rule wakes the agent on its first `tokens` events and none after. Where a refill interval of 0 ran before, from the starting rules, it refilled the bucket once, through a division by 0; it doesn't now. `wake_add_rule` and `addGatePolicy` refuse each.
- A gate.json that's a list, or whose `policies` isn't a list and holds something, or is missing or holds nothing beside a slip of it holding something, loaded as no rules under its default, and so did one whose rules sit under a name it doesn't read, such as `"policy"` or `"rules"`, where `policies` is missing or holds nothing: a list holding an object with a field of a rule, or of its match or behavior, is read as a slip of `policies` is. It's read that way, with a note, where the default is `"always"`, and isn't used where it's `"skip"` or `"defer"`, since every event would be held back. Under `"skip"` or `"defer"`, such a field at gate.json's top, where `policies` is missing or holds nothing, isn't used either, since it says a rule was meant; under `"always"` such fields load as before, with a note. A rule's `name`, a filter's `type` and a `keyBy` shape nothing on their own, so a label of the file can have their names: at the top, or as all a list's objects hold, they load as before, with a note, and so do a list holding no rule, such as `"comments": ["quiet for now"]` or `"notes": [{"date": "2026-10-01", "text": "muted"}]`, and a field of a rule or its match holding nothing, an empty list or an object holding only empty values, such as `"tagsAny": []` or `"match": {}`, since an empty one has always meant no constraint. A behavior, or one of its kinds, counts even when it holds nothing, as one does in a rule left out; a `null` or `""` is a field left out, in a list's objects as at the top. A label named as a field of a rule, such as `"source": "written by ops"`, counts as that field, since nothing in a name tells the two apart. A `policies` that isn't a list, or a slip of it, holding nothing, such as `"policies": {}` or `"polices": []`, writes no rules, as `[]` does: it loads as no rules, with a note saying what its default then does, and a change writes the list in place of such a `policies`, or beside such a slip. Beside a `policies` holding nothing, `[]` included, a slip of it holding something, a list of rules under another name and a field at the top that says a rule was meant are read as they are with no `policies`.
- A change through `wake_add_rule`, `wake_remove_rule`, `addGatePolicy` or `removeGatePolicy` edits gate.json's own list of rules by name: every rule it doesn't change is written back as it was written, with its problems and the fields the gate doesn't read, and the rules in force are read from what was written, so what gate.json still holds that the gate reads past or leaves out stays named until someone fixes it. A `"comment"` survives a write now, where a write used to write the rules as the gate held them. A rule a change leaves out of force, or gives another behavior, loses its counters, buckets and timers, as at a reload, so a rule that comes back, or that a change gives another behavior, starts afresh. Its pending debounce batch is then sent as its timer would have sent it, held while an agent is inferring or the host is quiesced, and so it is at a reload, which delivered it at once. A rule the gate leaves out can be replaced, or removed, by its name. A gate.json that's JSON the gate doesn't use is edited the same way, and only what loads is written: a change that doesn't mend what keeps it out is refused, naming that and what would bring it into force, and the file stays as its operator wrote it, where a change used to write the rules in force over it, losing its other rules, its own fields and its default; a change that replaces or removes by name the rule keeping it out brings it into force. When gate.json is missing, can't be read or isn't JSON, a change edits the list of the text whose rules are in force the same way, after keeping a copy of a gate.json that can't be read or isn't JSON, so a rule it leaves out keeps its name there too; the copy's log line, its listing in `keptCopies` and the tool's `keptUnreadable` now say gate.json "couldn't be used". A gate.json with no list of rules a change could edit without writing over or leaving out what it holds (a list, a `policies` that isn't one and holds something, a slip of `policies` holding something or rules under another name it doesn't read where `policies` is missing or holds nothing, a field at its top that says a rule was meant, under `"skip"` or `"defer"`, or JSON that isn't an object) refuses a change, an addition or a removal, and saves nothing; a removal there used to answer that no rule had the name, and an addition used to write the rules in force over the file, dropping such rules. A change refused because gate.json can't be read now says that whoever runs this host can make it readable, and that until then a change is refused the same way.
- `gate_status`'s `errors` says what the start did with the host's starting rules, apart from gate.json's load error, until the next start: how it read them, rules it couldn't use, and rules it couldn't add to gate.json. When adding the starting rules to a gate.json that loaded failed, the load that followed cleared the error, so the missing rules went unmentioned. When the start's own write of gate.json fails and leaves the rules in force unsaved, another entry says so until gate.json is written or loads; if that write leaves gate.json unable to load, the gate runs the rules it read and the ones it was adding, where it used to drop them, and that entry names what they hold that the gate reads past or leaves out. The entry for a gate.json that isn't used, or can't be read or isn't JSON, now says what's in force instead: the rules of the last gate.json the gate used, the rules a start read from gate.json and was adding when its write left gate.json unable to load, the host's starting rules, or none. `gate_status`'s `configSource` is `"initial"` while the starting rules are in force, where it said `"default"`.
- A `null` is a field left out, and so is `""`, which is named in a note, with what leaving it out does where that's more than no constraint: a `match` left out matches every event, and a `behavior` is `"always"`. In a rule the gate reads, a match left with nothing that narrows it, once something in it was dropped, left out as `""` or unread, matches every event, and a note says so; in a refusal of such a rule, where nothing was saved, the note says the rule as written would match every event. A gate.json holding `"channel": ""`, as `wake_add_rule` could save before, loads as it did, with the field left out. Where the gate refused a rule or a gate.json for one, in a `passthrough`, a behavior's kind or gate.json's `default`, it now loads without it. A `filter` whose `pattern` is `""` narrows nothing and is left out, with a note. For `wake_add_rule`, a `null` or `""` parameter is left out too, so a call whose only behavior is `null` is refused as one with none, where it was saved as `"always"`. A field name the gate reads nowhere that's no slip, such as `"comment"`, changes nothing, so it loads, and `gate_status`'s `errors` names it with the fields its place holds. `wake_add_rule` leaves it out of the rule it saves and names it in the result's `ignoredFields`, and `addGatePolicy` tells a new `onIgnoredFields` callback, or the log.
- `wake_add_rule` refuses a `position` other than `"append"` or `"prepend"`, and an `insertBefore` or `insertAfter` that isn't a string, which were ignored, so the rule was appended. A refused `behavior` points at `debounceMs`, `rateLimit` and `passiveSample`. Its description's example now gives `debounceMs: 60000` in place of `behavior: { debounce: 60000 }`, which its schema, a string enum, didn't admit.
- **What a deployment will notice:**
  - A gate.json holding a rule the gate refused before now loads, with that rule left out and named, under `"always"`, or where the rule skips, defers or has no tokens. A reload or a start applies its other rules, where a reload kept the rules the gate had and a start ran the host's starting rules, or none. So under `"always"`, a rule after the one left out that skips, defers, rate-limits or samples can now hold back an event those rules woke on, and one that debounces can delay it: that's the case where an event that woke the agent before can go quiet.
  - A rule that skips or defers, with a problem the gate read past before, is read as before, holding back every event it then matched, and now says so.
  - Under `"skip"` or `"defer"`, a gate.json whose rules sit under a name it doesn't read, or with a field at its top that says a rule was meant, where `policies` is missing or holds nothing, isn't used, where none of those rules loaded and its default held back what they were written to wake on. So is one whose label at the top is named as such a field, such as `"source"`, which held back every event.
  - `wake_add_rule` and `addGatePolicy` refuse a rule holding a field at another level than its own, and `wake_add_rule` a field of `match`, `rateLimit` or `passiveSample` given on its own; such a rule used to be saved without it. A gate.json written with such a field loads as before, with the field named.
  - A starting rule the gate refused before is named at start. One used to make the gate run all of the starting rules as given, from memory, so these ran and woke the agent: a `rate_limit` without `refillIntervalMs`, a `debounce` given as text such as `"60000"`, a `passthrough` that isn't a boolean, which ran as its truthiness, `passthrough: true` on `"always"`, and a rule with no `name` that wakes, such as on `"always"`. Now, under a starting default of `"always"`, such a rule is left out and the rest run; under `"skip"` or `"defer"`, none of the starting rules is used, and the start runs gate.json's rules, or none, which hears every event. connectome-host's recipes hold none of them.
  - A first start writes the host's starting rules to gate.json as given, a rule left out included, and runs each as read; gate.json, read the same way, names each problem at every load until someone fixes it. One refused rule used to keep any from being written. A later start adds, as given, the starting rules whose names gate.json lacks; a rule gate.json holds keeps its name even where the gate leaves it out, so the host's rule of that name doesn't replace the operator's.
  - A rule a slip already saved in a valid form, such as `"always"` saved from a typo or `match: {}` from a dropped field, loads as it was saved, since the slip is no longer in it.
