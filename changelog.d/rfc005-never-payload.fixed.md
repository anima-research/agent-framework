- **A reference an MCPL server marks `disposition: never` no longer reaches the agent or its tools.** RFC-005 §3.1 keeps a `never` payload out of model context. Before, nothing after parsing told `never` from `ref`. Such a reference was fetched like any other, eagerly when its claimed size was small, into the workspace's `refs/`, and its stub named the saved path, which the agent's workspace tools could open. Now the first `never` for a uri marks its reference's record: the reference's own, another reference's in the same result, or one inline data gives, an embedded resource's included, for a uri that already has a record. The mark stays for as long as the record does, whatever later deliveries say:
  - the framework fetches no such payload: `fetch_reference` answers that a server asked that its content never reach the agent, and the eager and script fetches pass it over;
  - its stub, and a script's object for it, name no saved copy, no fetch hint and no uri, and say why. A link to the uri is that stub too, and a script's object for the link carries no `uri`, where 0.27.0 read only the uri's latest testimony, so a link the host can't fetch showed its uri once that testimony carried no `never`. An image sent by that uri alone on a push, channel or injection lane is its stub, not a url for the provider;
  - a copy saved before the mark is no longer named or served, and the log says where it stays;
  - what this leaves: a `never` from any server marks the uri's record, so one server's `never` refuses later fetches of a uri another delivered. A copy saved before the mark stays in the workspace, where the agent's workspace tools can still find it. A record evicted past the registry's 2,000, or a restart, takes the mark with it. The workspace's earlier states, history and images the agent read before the mark keep what they held, and the agent isn't told that what it read is now `never`. No host-mediated use of a `never` payload is offered, RFC-005 §12's hand-off to a script included.
