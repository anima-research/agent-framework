- The persistent subconscious's note waiting with a tune-out cancel, when another cancel ends the hold first, goes out before that cancel's release, and where it can't be written the release says so, with the author and the error: the loss is stored and made durable with the release, or the hold doesn't end and the note waits on.
- A loss told to the persistent subconscious before a stop, in a release or by a notice, keeps the turn it asked for across the stop. Shown to it at rest, the row is in its window, where the boot's wake for rows still owed doesn't count it, so a boot asks that turn again for each such row its window shows with no turn of the subconscious's after it.
- A tune-out cancel that waited for held writes delivers its own note once its release is durable and before the hold's end is recorded, and makes the note durable too, so a crash between the end and the note can't lose the note untold with the hold no longer on record for the next boot to read. A note kept in memory as it is written (writes held from that write on) doesn't count as delivered: the hold stays in force, the cancel waiting for the writes, and a stop meanwhile tells the note lost.
- A reader's note kept in memory with its waiting tune-out cancel, whose store then fails when the writes are stored, is told lost to the reader, with the reason, when the hold ends, as the cancel's waiting answer promises, as well as to the operator (`message:lost` and the `store-held-lost` alert). Where the store can't tell whether the note landed, the reader is told that it may be lost. That holds too where the host stops, or the hold ends without the cancel, before the cancel's run tells it: the notice of that drop, the one a stop keeps in the store for the next boot included, says that whether the note was delivered isn't known, with the error, and not that it was lost. The note isn't written again.
- A reader's note kept in memory with its waiting tune-out cancel, and stored when the writes are stored, counts as delivered. Its cancel can still wait after that (writes are held again before it runs, or its run fails before it records the end), and a stop then tells nothing of the note. A release kept in memory that told a queued note's loss, once stored, is likewise not told again by a stop; where that release's store fails when the writes are stored, the note's author is told of the loss by a notice once the hold ends.
- A stop while an operator's change keeps a waiting cancel's writes in memory quiets the tune-out timers at once, waits for the operator's changes, and only then accounts for the cancels still waiting, so a cancel whose writes the change stores as it ends during the stop runs first, and the reader isn't told a note lost that the change's release stored. Such a cancel asks the resident's turn for its release, and the subconscious's report turn, after the host's queue has closed, so the stop drops them, and the release, shown to the resident at rest, is in its window, where the next start's wake for rows still owed doesn't count it. The stop's stamp records those turns (`wakesOwed`), and the next start asks each once, unless it asks that turn for a release of its own.
- A note or a release a waiting cancel's run stored counts as kept in memory by what its write answered, not by whether writes are held after the write: where writes are held only from just after it (a hold begun as the write returned), the cancel waits for the writes, and a stop meanwhile tells nothing of a note that landed.
- A stop given a budget whose wait for an operator's change runs out while that change still keeps a waiting cancel's note in memory doesn't tell the persistent subconscious the note was lost, since the change's release, later in the same process, may store it. The stop leaves that hold out of its stamp, naming the note as kept, and the next boot tells what that run's rows show: the cancel ran, with the note, where the note was stored, and that the note may be lost where it wasn't, as when a new instance on the same store handle starts before the old one's change has ended (nissa's house).
- A tune-out whose release reached the resident but whose end wasn't recorded (a budgeted stop whose wait ran out, or a throw between the release and the end, as a store fault would give) stays in force, but after the next start the resident read only "[Tune-out: … cancelled …]". The boot now tells the resident once, by a row after that release, that the release reached it but its end wasn't recorded, so the tune-out is still in force, what arrives is held for its next release, and how it ends. A check no longer counts or peeks as held the messages that release already delivered (Oscar, nissa's house).
- A loss notice whose own write begins a hold is written once: the kept write is stored at the hold's release, and the notice isn't written again.
- A boot after a crash credits the subconscious's own cancel where its call joined another waiting cancel after that cancel's release was written: the run that delivers a queued cancel's note names that cancel's askers on the note, so the boot's notice doesn't say a cancel "that wasn't yours" ran with the subconscious's own note.
- A note whose loss another cancel's release told, that release not made durable then, is traced (`tune-out:deferred-cancel-dropped`), and the persistent subconscious's turn to read it is asked for when the hold ends, by whichever run ends it.
- A cancel's release that meets a hold as it is written (a context manager that refuses its work from that write on) doesn't record the hold's end over a release kept in memory only: the cancel waits for the writes, the tune-out in force (`{ ok: true, deferred: true }`), and its run once they are stored finds that release and records the end. A stop meanwhile (a trace listener's, of that write) tells the cancel as it tells one it finds waiting, its note's loss kept in the store; and a hold such a listener begins on that channel, or a new all-except hold, keeps its timers when the run's own note is then told lost.
- A cancel asked for with a note while an earlier cancel of the same hold is running (from a trace listener, writes held) doesn't replace that one's note when the earlier one waits again: the earlier cancel stands with its note, and the later one's note is told dropped to its author (`tune-out:deferred-cancel-dropped`, `superseded`), its caller having been answered as waiting. Where the earlier cancel's run has delivered its note already, and failed before recording the end, the later note waits with it and goes out when the hold ends, whether it joined during the run or after.
