- **Hosts and scripts that fetch a reference a server marked `never` (RFC-005's `disposition: never`) through the framework, and modules whose results restate a server's reference:** such a fetch is now refused, and a module's claims about a server's reference no longer replace the server's. No MCPL server is known to send `never` today. While a reference is marked `never`, the framework doesn't fetch or save its payload, and forgets the path of a copy saved earlier. RFC-005 §3.1 keeps a `never` payload out of model context, and here every consumer of a fetched payload, a script included, returns its output to the model. Before, nothing after parsing told `never` from `ref`. Such a reference was fetched like any other, eagerly when its claimed size was small, into the workspace's `refs/`, and its stub named the saved path, which the agent's workspace tools could open. Now the first `never` in an MCPL server's own content (a tool result, an error result, or a push, channel or injection) marks its uri's record: the reference's own, another reference's in the same result, or one inline data gives, an embedded resource's included, for a uri that already has a record. The log names the server whose content made the mark and the servers the record is bound to. On a push, channel or injection lane, a `never` anywhere in a message governs every block of it, whatever their order, so an image sent by uri before a `never` for that uri is its stub. A server's `never` reference nested in its tool result, an error result included, at any depth the result's text shows, marks a record for its uri, bound to that server. A `never` in any other result, such as a module's, keeps its payload out of that result alone: nothing that handles the result fetches it, and its stubs and script objects give the reason and name no saved copy or uri. A registration that knows no server, such as a module's result's, no longer replaces what a server's reference said (its digest, expiry or disposition): a fetch reads the server's own testimony. The mark stays for as long as the record does, whatever later deliveries say:
  - the framework starts no fetch of such a payload and saves none of it, and a fetch already under way stops at its next chunk: `fetch_reference` answers that a server asked that its content never reach the agent, and the eager and script fetches pass it over. A result whose blocks can't be read for a nested `never`, such as one too deep to convert, gets no eager or script fetch at all, and where a model's call has a reference to pass over, the log says so (a script whose view can't be read gets the call's result as one that couldn't be converted);
  - its stub, and a script's object for it, name no saved copy, no fetch hint and no uri, and say why. A link to the uri is that stub too, and a script's object for the link carries no `uri`, where 0.27.0 read only the uri's latest testimony, so a link the host can't fetch showed its uri once that testimony carried no `never`. An image sent by that uri alone on a push, channel or injection lane is its stub, not a url for the provider;
  - an embedded resource for the uri shows a notice saying why, not its contents, whatever they are, on every lane, in history and to a script, and so does one beside a `never` for its uri in the same message or result, whatever their order;
  - a copy saved before the mark is no longer named or served, and the log says where it stays;
  - what this leaves: a `never` from any server marks the uri's record, so one server's `never` refuses later fetches of a uri another delivered. A `never` in a module's result, rather than a server's, marks nothing, and doesn't follow the uri into later results once a server has spoken for it. A copy saved before the mark stays in the workspace, where the agent's workspace tools can still find it, and so does one whose save finished as the mark came, if deleting it fails; the log says where it is. An inline `never` read before any reference for its uri, in an earlier result or message, marks nothing, so a later plain reference makes an unmarked record. A reference in a result whose blocks can't be read for a nested `never` isn't marked by that `never`, so the agent's own `fetch_reference` can still fetch it. A record evicted past the registry's 2,000, or a restart, takes the mark with it. The workspace's earlier states, history and images the agent read before the mark keep what they held, and the agent isn't told that what it read is now `never`. An image sent by uri alone before the mark stays a url in history, so the provider fetches it again for each request that carries its message, until a fold takes it. RFC-005 governs the server-to-host content blocks of tool results, push events, channel messages and injections (§4), and so does this: a modern or MCP-only server's results, which don't speak RFC-005, and any result's structured content, which is tool-defined JSON, show as they did, uris and embedded contents an MCPL server marked `never` included. No host-mediated use of a `never` payload is offered, RFC-005 §12's hand-off to a script included.
