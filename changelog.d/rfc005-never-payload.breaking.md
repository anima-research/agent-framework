- **Hosts and scripts that fetch a reference a server marked `never` (RFC-005's `disposition: never`) through the framework, and modules whose results restate a server's reference:** such a fetch is now refused, and a module's claims about a server's reference no longer replace the server's. No MCPL server is known to send `never` today. While a reference is marked `never`, the framework doesn't fetch or save its payload, and forgets the path of a copy saved earlier. RFC-005 §3.1 keeps a `never` payload out of model context, and here every consumer of a fetched payload, a script included, returns its output to the model. Before, nothing after parsing told `never` from `ref`. Such a reference was fetched like any other, eagerly when its claimed size was small, into the workspace's `refs/`, and its stub named the saved path, which the agent's workspace tools could open. Now the first `never` in an MCPL server's own content (a tool result, an error result, or a push, channel or injection) marks its uri's record: the reference's own, another reference's in the same result, or one inline data gives, an embedded resource's included. Where the uri has no record, the `never` makes one, marked and bound to that server, so a later delivery of the uri finds the mark, unless the uri is longer than a reference's link may be. The log names the server whose content made the mark and the servers the record is bound to. On a push, channel or injection lane, a `never` anywhere in a message governs every block of it, whatever their order, so an image sent by uri before a `never` for that uri is its stub. A server's `never` reference nested in its tool result, an error result included, at any depth the result's text shows, marks its uri's record, binding that server where no server had, or, where the uri has none, one made for it, bound to that server. A `never` in any other result, such as a module's, marks nothing but keeps its payload out of that result: nothing that handles the result fetches it, and each reference to such a uri shows its name, if it has one, and a notice that its content is marked `never`, with no id to fetch it by and no saved copy or uri, unless a server's `never` already marked that uri's record, whose stub it then shows, with an id a fetch refuses. An id a server's own delivery gave earlier still fetches it. A registration that knows no server, such as a module's result's, no longer replaces what a server's reference said (its digest, expiry or disposition): a fetch reads the server's own testimony. Where no server has spoken for a uri, a later such registration, other than a link's, still replaces an earlier one's, as before. The mark stays for as long as the record does, whatever later deliveries say:
  - the framework starts no fetch of such a payload and saves none of it, and a fetch already under way stops at its next chunk: `fetch_reference` answers that a server asked that its content never reach the agent, and the eager and script fetches pass it over. A result whose blocks can't be read for a nested `never`, such as one too deep to convert, gets no eager or script fetch at all, and where a model's call has a reference to pass over, the log says so (a script whose view can't be read gets the call's result as one that couldn't be converted);
  - its stub, and a script's object for it, name no saved copy, no fetch hint and no uri, and say why. A link to the uri is that stub too, and a script's object for the link carries no `uri`, where 0.27.0 read only the uri's latest testimony, so a link the host can't fetch showed its uri once that testimony carried no `never`. An image sent by that uri alone on a push, channel or injection lane is its stub, not a url for the provider;
  - an embedded resource for the uri shows a notice saying why, not its contents, whatever they are, on every lane, in history and to a script, and so does one beside a `never` for its uri in the same message or result, whatever their order;
  - a copy saved before the mark is no longer named or served, and the log says where it stays, unless the record that named it was evicted before the mark;
  - what this leaves: a `never` from any server marks the uri's record, so one server's `never` refuses later fetches of a uri another delivered. A `never` in a module's result, rather than a server's, marks nothing, and doesn't follow the uri into later results once a server has spoken for it. A copy saved before the mark stays in the workspace, where the agent's workspace tools can still find it; the log says where, unless the record that named it was evicted before the mark. So does one whose save finished as the mark came, if deleting it fails, and the log says where that one is. On a mount without autoMaterialize, deleting it leaves a disk copy a materialize wrote in the meantime, listed as workspace-deleted, until materialize with applyDeletions removes it or a sync of the path restores it. A reference in a result whose blocks can't be read for a nested `never` isn't marked by that `never`, so the agent's own `fetch_reference` can still fetch it. A record evicted past the registry's 2,000, or a restart, takes the mark with it. A `never` for a uri longer than a reference's link may be makes no record, so outside the result or message that carries it, an embedded resource for that uri shows its contents unless it carries its own `never`. A `never` on a block rejected whole for its uri's length governs nothing, since RFC-005 §8 rejects such a block whole, its `disposition` included, so an embedded resource for that uri beside it shows its contents. A mark is on the uri as sent. Another spelling of it that shows as the same text, such as one with whitespace at either end or a control or bidi character added, has a record of its own, which the mark doesn't reach, so a later fetch of it isn't refused and a later delivery of it shows as an unmarked one does. Within the result or message that carries the `never`, a reference or link so spelled is still withheld by that `never`, as before, but an image sent by uri alone or an embedded resource so spelled isn't. The workspace's earlier states, history and images the agent read before the mark keep what they held, and the agent isn't told that what it read is now `never`. An image sent by uri alone before the mark stays a url in history, so the provider fetches it again for each request that carries its message, until a fold takes it. RFC-005 governs the server-to-host content blocks of tool results, push events, channel messages and injections (§4), and so does this: a modern or MCP-only server's results, which don't speak RFC-005, and any result's structured content, which is tool-defined JSON, show as they did, uris and embedded contents an MCPL server marked `never` included. No host-mediated use of a `never` payload is offered, RFC-005 §12's hand-off to a script included.
- **Servers that send an image or audio by a uri longer than a reference's link may be on a push, channel or injection:** such a block is now rejected whole, whatever its disposition, as a reference with such a uri already was, and as RFC-005 §8 says of a block whose uri violates its schema. The limit is RFC-005's 4,096, counted in UTF-16 units, as a reference's always has been, so a uri of 4,096 code points or fewer that holds characters outside the Basic Multilingual Plane can pass it. The agent reads that its link is longer than this host accepts, where an image with no disposition went to the provider as a url and audio with none showed that it carried no data.
