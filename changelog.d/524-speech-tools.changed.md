- A call of `reply_to_message`, telegram-mcpl's reply, is an explicit send, by that name on any server: it holds the round's plain speech as a send does, where it posted when its answer gives a `channelId` the framework knows, and for every destination when it doesn't, as telegram-mcpl's plain-text answer doesn't, a failed reply's included, since telegram-mcpl doesn't flag its failures. In locus or hybrid routing, a `code_execution` script that names it makes its round wait before its prose is routed, as one that names `send_message` does.
- `history--extract`'s text form shows a call of `channel_publish`, `send_message`, `reply_message`, `send_dm`, `reply_to_message`, `send_file`, `send_scheduled_message`, `create_poll`, `edit_message`, `upload_file`, `say` or `whisper`, by that name on any server, as its name and its words when it carries any, such as `[telegram--send_message] …`, where it showed `[tool_use: telegram--send_message]` with the words left out. A call of any other tool, or one with no words, shows as before. A failed tool result shows as `[tool_result: NAME, error]`, or `[tool_result, error]` when it has no name, where it showed `[tool_result: NAME]` or `[tool_result]`, so a send whose server reports it failed doesn't read as sent. The send's own label carries the same mark when its result, stored after it, failed: `[telegram--send_message, error] …` in `history--extract` and in `history--search`'s and its regex search's snippets, and `[send_message, error] …` in `history--semantic_search`'s hits, so a hit on a failed send gives the account `history--extract` gives. A search snippet whose match falls in a send's words starts with the send's label, marked so when its result failed, and then shows the words around the match, so the label stays in a snippet cut from a long message. Its description says so, so an agent with the history tools sees its tool list change once.
