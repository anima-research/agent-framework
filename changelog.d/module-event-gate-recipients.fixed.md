- A module's process response that asks inference for named agents, for an event other than an MCPL push or channel message (those are gated as they arrive): when a gate rule batches the event (`debounce`), it now wakes only those of them that its source can trigger and that read the slot its messages land in, and the batch's `[Gate: …]` line quotes the event to them alone. Before, it woke every agent the gate wakes and was quoted to each of them, outside its messages' audience. A named agent that doesn't read that slot, such as an isolated job, isn't named in the batch, since a line for agents none of whom read the slot is stored as a write that names no agent, which every resident reads. When the response names no agent a batch could name, the rule lets its event through, so inference is asked for the job as with no rule, when its view shows a message the response stores, where it stores any; before, the batch woke the residents instead. A job named beside a resident isn't asked under the rule, as before: the event is batched for the resident. A response asking inference for every agent (`requestInference: true`) is unchanged. One asking it for an empty list (`requestInference: []`) now wakes no one in a batch, as it wakes no one when nothing batches it. For any event, a named agent is now woken, batched or not, only when the response stores no message or one that agent's view shows, read as the message is stored: a message held from the residents (a tune-out's `tuneOut`) wakes a subconscious the response names, whose view keeps held traffic, and not a resident, whose woken turn carried nothing it could see.
- In a gate batch that also holds events naming their recipients, an untargeted event, one with no list of recipients, is now shown only to the gate's own recipients, and an event naming its recipients only to them: a named recipient the gate doesn't otherwise wake, such as a subconscious, no longer gets the batch's untargeted events in its line. An event whose list of recipients is empty joins no batch, so it neither restarts a batch's quiet period nor takes room in it, and a batching rule lets it through, as `always` does, so whom it wakes is the caller's. An agent's upcoming wakes count a pending batch only when it would wake that agent. A judge rule still judges a batch as a whole, for the gate's own recipients, and the reply judge is now told only the upcoming wakes of the agent whose context it reads: before, it was told every gate recipient's, such as another resident's self-wake or a batch for another resident alone, as that agent's.
